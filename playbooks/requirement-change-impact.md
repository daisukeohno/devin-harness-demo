# Playbook: 要求変更の影響分析と修正

## 目的

仕様変更が来たときに、影響範囲の洗い出しから検証まで同じ順序で進める。
実装前に人が計画を見て止められるようにする。

## 入力

- 変更要求: <例: 異常判定を 3σ 固定から、デバイスごとの過去 7 日分布に基づく判定に変える>
- 背景・理由: <なぜ必要か>
- 制約: <互換性、期限、変えてはいけないもの>

## 手順

1. `@skills:impact-analysis` を実行する。この段階ではコードを変更しない。
2. 分析結果（影響範囲、互換性への影響、方針案 A/B、検証計画）を提示し、人の承認を待つ。
3. 承認された方針で実装する。設定値は `config.py` に追加し、既定値は現行の振る舞いを保つ。
4. テストを追加する。少なくとも「正常系」「全欠損」「サンプル数不足」の 3 ケース。既存テストの期待値を書き換える場合は、その理由を PR に書く。
5. `@skills:local-testing` を実行する。
6. 変更前後で、サンプルデータに対する異常検知件数を比較して表にする。
7. PR を作り、手順 2 の分析結果と手順 6 の比較を本文に載せる。`AGENTS.md` / `REVIEW.md` の更新が必要なら同じ PR に含める。

## 成果物

- 影響範囲分析（セッション内）
- 実装とテスト（PR）
- 変更前後の数値比較（PR 本文）

## 人が承認するポイント

- 手順 2 の方針選択
- 既定値を変える場合の可否
- API レスポンスの互換性を崩す場合の移行方法

## 完了条件

- CI が緑
- 既定設定では既存の出力が変わらないことをテストで示している
- 影響を受ける運用レポートが列挙されている
