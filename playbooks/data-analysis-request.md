# Playbook: センサーデータの解析依頼

## 目的

新しいデータや新しい問いに対して、品質確認から結論までを同じ手順で回す。
毎回同じ品質の中間成果物（品質レポート、特徴量の根拠、検証結果）が残るようにする。

## 入力（セッション開始時に人が埋める）

- 対象データ: <パスまたはテーブル名。無ければ同梱のサンプルデータ>
- 問い: <例: dev-001 の温度異常が増えているか、増えているならいつからか>
- 成功条件: <例: 異常件数の推移と、しきい値を変えた場合の感度が示されている>
- 期限と粒度: <例: 30 分以内に一次報告>

## 手順

1. `@skills:data-quality-check` を実行し、結果を表で提示する。欠損率が 5% を超える場合はここで一度止めて報告する。
2. 問いを検証可能な形に分解する。「増えているか」なら、比較期間、集計単位、有意と見なす差を明示する。
3. 分析を実装する。既存の `sensor_analytics.analysis` の関数を使い、足りない場合は関数を追加してテストも書く。アドホックなスクリプトをリポジトリに残さない。
4. 結果を出す。図を作る場合は元データの行数と期間を図の中に入れる。
5. 解釈を書く。データから言えることと、言えないことを分けて書く。しきい値やウィンドウ幅に結論が依存する場合は、感度も示す。
6. 変更をコミットして PR を作る。PR 本文に手順 1 と 4 の結果を貼る。

## 成果物

- 品質レポート（セッション内に表で提示）
- 解析コードとテスト（PR）
- 結論と限界の記述（PR 本文とセッション内の両方）

## 人が承認するポイント

- 手順 1 で品質に問題があった場合の進め方
- 手順 2 で決めた比較条件
- 手順 5 の解釈のうち、運用判断につながる部分

## 完了条件

- `uv run pytest` と `uv run ruff check .` が通っている
- 報告した数値すべてに `n_samples` / `n_dropped` が併記されている
- 「言えないこと」が 1 行以上書かれている
