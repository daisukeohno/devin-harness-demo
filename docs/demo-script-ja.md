# デモ台本（15〜20分）

「Devin はコードを書くだけではなく、組織の前提と手順を設定として持ち込める」ことを見せる回です。
コードそのものより、**Knowledge / Skills / REVIEW.md / Playbook / Blueprint の役割分担**を見せます。

## 事前準備（前日まで）

1. このリポジトリを Devin の組織に接続する
2. `knowledge/*.md` を Knowledge に登録する（`knowledge/README.md` の手順）
3. `playbooks/*.md` を Playbook に登録する
4. `blueprint.yaml` の内容を Settings > Environment に登録し、スナップショットを 1 回ビルドしておく
5. Devin Review を有効にし、必要なら Settings > Review の Review Rules を確認する（`**/REVIEW.md` は既定で読まれます）
6. `./scripts/make_demo_pr.sh --push` で、わざと問題のある PR 用ブランチを push しておく（PR は当日その場で作ると流れが良い）

所要 20 分ほど。当日その場でやるとビルド待ちが発生するので前日に済ませます。

## 全体の見せ方

Devin の 4 つのレイヤーに沿って進めます。

| レイヤー | このデモで見せるもの |
|---|---|
| Deep Wiki | リポジトリの構造理解（時間がなければ省略可） |
| Ask Devin | 読み取り専用の調査。影響範囲の洗い出し |
| Devin Sessions | Playbook を付けた実行。テスト、PR 作成 |
| Devin Review | `REVIEW.md` の観点に沿った PR レビュー |

## パート 1: 設定がどこにあるか（3分）

画面はリポジトリのファイルツリー。

- `.agents/skills/` を開く。「手順を Markdown で置くと、Devin が自動で見つけて使います。テスト手順、データ品質チェック、影響範囲分析、リリース手順を入れています」
- `AGENTS.md` を開く。「プロジェクト共通の決めごと。セッションとレビューの両方が読みます」
- `REVIEW.md` を開く。「レビューで何を見るか、何を見ないかを書く場所。`src/sensor_analytics/REVIEW.md` のようにディレクトリ単位で追加もできます」
- Web アプリの Knowledge を開く。「コードを読んでも分からない前提はこちら。物理的な測定範囲、メンテナンス窓、やってはいけない前処理などを入れています」

ここで一言: 「モデルの賢さで補うのではなく、前提と手順を設定として渡す。ここが再現性の差になります」

## パート 2: Ask Devin で現状を掴む（4分）

プロンプト 1（Ask モード）:

```
このリポジトリの解析パイプラインで、欠損値と時系列分割の扱いが
Knowledge に書かれた制約に違反している箇所を洗い出してください。
```

プロンプト 2（Ask モード）:

```
異常判定を 3σ 固定からデバイスごとの過去 7 日分布ベースに変えたい場合の
影響範囲と検証計画を、@skills:impact-analysis に従って出してください。
```

見せどころ: コードを変更せずに、影響ファイル・互換性・検証計画・確認事項が出てくること。
Skill を指定したことで出力フォーマットが揃うこと。

## パート 3: Playbook を付けて実行（6分）

プロンプト 3（通常セッション、Playbook を添付）:

```
@playbook:<requirement-change-impact の ID> パート 2 で出した方針 A で実装してください。
既定設定では既存の出力が変わらないことをテストで示してください。
```

見せどころ:

- Playbook の「人が承認するポイント」で止まること
- `@skills:local-testing` が呼ばれ、lint とテストとスモークテストが実行されること
- PR 本文に変更前後の異常検知件数の比較が入ること

時間が足りない場合は、事前に走らせたセッションを開いて結果を見せます。

## パート 4: Devin Review（4分）

`demo/review-findings-*` ブランチから PR を作成する。

見せどころ: `REVIEW.md` に書いた観点どおりの指摘が出ること。仕込んでいる問題は 4 つです。

1. 欠損値の 0 埋め（Knowledge のデータ制約違反）
2. しきい値のハードコード（`config.py` を経由していない）
3. `n_samples` / `n_dropped` を返していない新関数（`src/sensor_analytics/REVIEW.md` の観点）
4. naive datetime と UTC datetime の比較（`AGENTS.md` の決めごと違反）

「同じ指摘を人が毎回するのは無理があります。観点をファイルに書いておけば、レビューの基準が揃います」

## パート 5: 設定の持ち帰り方（2分）

- Skills と REVIEW.md はリポジトリの中なので、Git のレビューを通して育てられる
- Knowledge と Playbook は組織横断の資産。リポジトリをまたいで使える
- Blueprint で環境構築を固定できるので、セッション開始時のセットアップ待ちがなくなる
- 社外に出せないデータやライセンスが必要なツールを使う場合は、顧客インフラ上でセッションを動かす構成（Outposts）を相談する

## 話すときの注意

- 「自動で全部やります」とは言わない。承認ポイントがどこにあるかを必ず見せる。
- 未検証の構成（顧客環境固有の連携、ライセンス必須ツール、実機接続）は「こう組める」と「一緒に確かめたい」を分ける。
- サンプルデータは合成データだと明言する。精度の話には使えない。
